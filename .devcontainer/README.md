# Optional Dev Container

This development environment uses Python 3.14 and Postgres 16, matching the
pipeline's CI versions. The native setup, research database, scheduled jobs and
deployed portal are unchanged.

## Open In VS Code

1. Start Docker Desktop and ensure the VS Code **Dev Containers** extension is installed.
2. Open this repository and run **Dev Containers: Reopen in Container** from the command palette.
3. In the container terminal, run `python -m pytest -q -rs`.

Opening builds the image automatically; later opens reuse cached layers.
The build is an explicit `initializeCommand` because Compose 5.6's build runner
rejects the out-of-context temporary Dockerfile generated by Dev Containers CLI
0.89. Only the checked-in Dockerfile and dependency lock enter the build context.

The container runs as the non-root `vscode` user. Python and installed packages
live in `/opt/venv`; do not activate the host's `.venv` inside the container.
Repository edits are shared with the Mac. VS Code includes Python, Pylance and
Copilot extensions, with pytest discovery enabled.

No ingestion, LLM generation, publication or scheduled job runs automatically.

## Databases And Configuration

| Service | Database | Lifetime |
| --- | --- | --- |
| `dev-db` | `meridian_dev` | Persists in the `meridian-dev_dev-data` Docker volume |
| `test-db` | `meridian_test` | Disposable tmpfs; contents disappear when the container stops |

Both databases load the repository's schema and lookup seeds on first startup.
They contain no copy of the research data. No database port is published on the
Mac, so an existing server on port 5432 is unaffected.

`DATABASE_URL` points to `dev-db`; `GACC_TEST_DATABASE_URL` points to `test-db`.
The test fixtures truncate tables, so never change the test URL to a database
containing research data. The default development database is separate from the
one tests erase.

The container sets `PYTHON_DOTENV_DISABLED=1`, and the Python extension's
`python.envFile` is `/dev/null`. Existing host environment files are not loaded
automatically. Any additional configuration or credentials must be supplied
explicitly in the container session, without committing them.

The repository is still mounted read-write, including gitignored files such as
environment files. This is not a hardened sandbox. The configuration does not
mount your home directory or Docker socket and does not request privileged
mode, extra Linux capabilities or relaxed seccomp restrictions.

Persistent volumes are not backups. Rebuilding the Python image does not migrate
an existing development database: apply schema migrations there deliberately,
as with the native setup. To reload the latest schema into only the disposable
test database, run this from the repository root on the Mac:

```sh
docker compose -f .devcontainer/compose.yaml restart test-db
```

Wait for `test-db` to become healthy before running tests. Do not remove the
development data volume unless its contents are intentionally disposable too.
This initial configuration uses a single `meridian-dev` Compose project; do not
run independent worktrees concurrently with the same project name.

## Host Ollama

Ollama stays on macOS, preserving native GPU acceleration on Apple Silicon.
The container uses `OLLAMA_HOST=http://host.docker.internal:11434`.

Start your native Ollama server when needed. Its listening address and Docker
Desktop networking must permit connections from the container. Do not expose
Ollama to the LAN just to make this work. During initial validation no server
was listening on the host's default port, so model generation is not verified.
Tests use fake backends and do not require Ollama or cloud credentials.

## Dependency Updates

`requirements.lock` contains pinned versions and hashes resolved from the root
requirements files for Python 3.14. Only the container uses this lock; the native
and CI dependency-installation workflows are unchanged. After changing the root
requirements, refresh the lock intentionally from the repository root on the Mac:

```sh
docker run --rm \
  --mount "type=bind,source=$PWD/requirements.txt,target=/inputs/requirements.txt,readonly" \
  --mount "type=bind,source=$PWD/requirements-dev.txt,target=/inputs/requirements-dev.txt,readonly" \
  --mount "type=bind,source=$PWD/.devcontainer,target=/output" \
  ghcr.io/astral-sh/uv:python3.14-trixie-slim \
  uv pip compile /inputs/requirements-dev.txt --python-version 3.14 \
  --universal --generate-hashes --upgrade --output-file /output/requirements.lock
```

Review the lock changes, use **Dev Containers: Rebuild Container**, then rerun
the full test suite. Dependencies are installed with pip's `--require-hashes`.
The Python and Postgres image tags track patch releases rather than immutable
digests; the environment is not intended to be a bit-for-bit archival build.

The image scanner reported six high-severity advisories and no critical ones
during initial validation on 2026-10-24. This setup is not a clean security audit.
Refresh and rescan base images as upstream fixes become available:

```sh
docker build --pull --tag meridian-dev-python:local .devcontainer
docker scout cves --only-severity critical,high local://meridian-dev-python:local
```

## Command-Line Use And Shutdown

These commands run from the repository root on the Mac. The CLI requires Node.js;
VS Code users do not need to install it separately for the editor workflow.

```sh
npx --yes @devcontainers/cli@0.89.0 up --workspace-folder "$PWD"
npx --yes @devcontainers/cli@0.89.0 exec --workspace-folder "$PWD" python -m pytest -q -rs
docker compose -f .devcontainer/compose.yaml stop
```

The editor is configured to stop the Compose services when the dev-container
session closes. Stopping preserves the development volume but clears test data.
Reopen the container to start the services again.
